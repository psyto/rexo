# Rexo — Credential-Layer MVP (背骨の差し替え)

**Version:** 0.2
**Status:** Supersedes the Pillar-1 (marketplace) framing in v0.1
**Backbone:** 柱2 — 検証可能な実行実績・信用レイヤー

このドキュメントは v0.1（01〜04）の**背骨を差し替える**。v0.1 は「再利用スキルの売買所（柱1）」を主役に、実績スコア（柱2）を装飾として載せていた。本 MVP はそれを逆転する。

> **MVP = 人 / AI エージェントの実行実績を、顧客の秘密を漏らさず、第三者が独立に再計算して検証できる信用レイヤー（credential）。**
> スキル再利用・ロイヤリティ（柱1）は信用が成立した後に上へ接ぐ。将来計算資源への与信（柱3）は MVP 外を維持する。

## 0. なぜ柱2が背骨か（3行）

1. **秘密からの分離が設計で保証される** — 信用の単位は秘密ゼロの Proof Receipt。redact したら空になる問題を構造的に受けない。
2. **堀がここにしかない** — 独立検証（C型の堀）= 既存 `reexec-core` がそのまま信用エンジンになる。マーケットプレイス（柱1）は流動性コールドスタートで堀ゼロ。
3. **demand が今ある** — 「このエージェント / 制作者の "can" 主張を信じてよいか」は現在進行形の未解決の痛み。しかも機械検証できる。

## 1. v0.1 からの差分（生きる / 変わる / MVP外）

| v0.1 の要素 | v0.2 での扱い | 理由 |
|---|---|---|
| Execution Trace（端末内・暗号化） | **生きる** | 信用の原資。変更なし |
| Proof Receipt | **昇格して主役**。単なる公開サマリではなく「独立に再計算された検証済みクレーム」に再定義 | §3 |
| Capability Score | **昇格して主役**。買い手が読む中心成果物 | §3 |
| Skill Capsule（再利用可能な実行資産） | **降格・後回し**。MVP では実行資産ではなく *信用オブジェクト*（何を、どの条件で、どれだけ良くやったかの束）として扱う | 柱1は後付け |
| LicenseEscrow / ロイヤリティ分配 / 決済 | **MVP から外す** | マーケットが無い段階では不要。信用成立後 |
| Reviewer 報酬プール / 異議処理 | **縮小**。人手レビューは「機械再計算できない主張」に限定 | §4 |
| CapsuleRegistry（チェーン） | **縮小して残す**。Receipt コミットメントのアンカーのみ。エスクローは載せない | §5 |
| 将来計算資源への信用枠（柱3） | **切ったまま** | 無担保実績与信は歴史的に呪われた領域。柱2が本物になって初めて下流に来る |

**要点:** MVP から二面マーケット・エスクロー・ロイヤリティが消える。つまり **MVP はマーケットプレイスではないので、コールドスタート問題を負わない。** 必要なのは「実績を証明したい供給側 N 人」と「誰でも無料で検証できる導線」だけ。

## 2. 最初の買い手と wedge（demand）

供給側が「信頼で差別化するために対価を払う」構造を取る。二面流動性を要求しないので立ち上がる。

- **一次買い手 = AI 支援制作を売る Maker / エージェンシー。** 「AI で速い・安い」が飽和した市場で、*独立検証された実績*は数少ない実効的な差別化。Maker は「検証済みポートフォリオ」を新規案件の受注に使うために払う。
- 検証は誰にでも無料。買い手（発注者）はコストゼロで Maker の "can" を確認できる → 供給側が集まる理由が生まれる。
- **一次成果物 = 検証可能ポートフォリオ**。「直近 N 件の AI 制作サイトについて、顧客の秘密を出さずに、独立再計算した Lighthouse / 表示速度 / 修正回数 / コスト帯の Receipt を並べた1枚」。フリーランス / エージェンシーが次の顧客を取るために見せる具体物。
- 後続買い手候補（MVP では狙わない）: 発注者側の検証需要、エージェント・オーケストレーション基盤のトラスト・プリミティブ。

来週テストできる最小形: **実在の完了案件1件で、顧客の秘密を一切見せずに、第三者が主張を検証できる Proof Receipt を1枚発行する。**

## 3. 単位の再定義

### Proof Receipt（主役）

「Maker が署名した JSON」では信用にならない。**独立検証者が、コミット済みアーティファクトから *再計算* した検証済みクレーム**であること。

- **コミット:** 出力（公開 URL / repo / artifact）のハッシュ、trace の tool / cost / time / 修正回数を salt 付きでコミット。
- **再計算:** 検証者が独立にコミット済みアーティファクトへ評価器を回す（Lighthouse、リンク検査、レスポンシブ、a11y、artifact ハッシュ一致）→ メトリクスを *生成* → 署名。**Maker はメトリクスを偽造できない（検証者が計算したから）。**
- **選択的開示:** 買い手は特定クレームだけを、秘密本文を見ずに検証できる。

### メトリクスの2階層（過大主張を防ぐ設計線）

| 種別 | 例 | 検証の強さ |
|---|---|---|
| **機械再計算可能** | Lighthouse、表示速度、リンク切れ、レスポンシブ、a11y、artifact ハッシュ、tool / cost / 修正回数 | **強**（検証者が独立再計算 → 偽造不能） |
| **成果・アテステーション依存** | CVR、返信率、「見落とし削減」 | **弱**（顧客のライブ解析が必要 → 検証者は再計算できない。顧客署名アテステーションとして *明示ラベル付き* で低信頼扱い） |

MVP は**機械再計算可能メトリクスを主役**にし、CVR 等は「顧客アテステーション（低信頼）」と明記して並べる。ここを混ぜないことが誠実さと堀の両方を守る。

### Capability Score（主役）

Capsule / Agent が特定条件下で再現した、独立再計算メトリクスの束と、そのサンプル数・根拠。単一総合点は出さない（v0.1 FR-41 を継承）。

## 4. `reexec-core` の再利用（具体）

この MVP は最終製品を一から積まない。既存 PUBLIC `reexec-core` を**検証基盤**として薄く投影する（Intentio の thin 化と同じ判断）。

| 必要能力 | reexec-core から再利用 |
|---|---|
| 決定的な再実行ハーネス（アーティファクトへ評価器を回す） | 再実行エンジン本体 |
| コミットメント + 256-bit salt | commitment scheme |
| 選択的開示（特定クレームのみ検証） | disclosure primitive |
| 検証者署名・第三者再現 | verifier signature |

Rexo 側が新規に書くのは:（a）Web 制作評価器のアダプタ、（b）Receipt / Capability Score のスキーマと表示面、（c）Maker の redact・承認 UI。**検証の核は既存エンジン。**

## 5. チェーンの役割（縮小）

- `ReceiptRegistry`: Receipt コミットメントと検証者署名ルートのアンカーのみ。本文・エスクロー・分配は載せない。
- テストネット開始。EVM L2 か Solana 低コスト環境を1つ。
- **MVP に資金保管契約は無い**（エスクロー / 決済は柱1と一緒に後付け）。

## 6. MVP outcome / success metrics（書き直し）

**Outcome:** 実在の AI 制作案件から、顧客の秘密を出さずに独立検証された Proof Receipt を発行し、第三者がその主張を再現検証でき、Maker がそれを受注文脈で「見せたい」と評価すること。

- Maker 10 人のうち **6 人以上**が、生成された検証済み Receipt を「案件獲得に使いたい」と回答（redact 後も価値が残った証拠）。
- Receipt の **機械再計算メトリクスを、第三者が独立に再現検証**できる（署名・コミットメントの検証が第三者で成立）。
- 生プロンプト・顧客 PII・API キーが公開メタデータ / 台帳に **一件も残らない**。
- 買い手（発注者役）**3 人以上**が、Receipt を見て「この主張を信じる根拠になる」と回答。

## 7. MVP user journeys（マーケット無し版）

### A. Maker: 完了案件を検証済み Receipt にする
1. パスキー / メールでログイン（ウォレット非表示）。
2. SDK / 拡張で制作作業を記録、または完了済みアーティファクトの URL / repo を登録。
3. AI が redact 済み Trace から Receipt 草案を生成。生プロンプト・顧客データは端末内 Vault のみ。
4. Maker が公開項目を差分画面でレビュー・削除・承認（自動公開禁止）。
5. **検証者が独立にアーティファクトへ評価器を再計算** → 署名 → コミットメントをアンカー。
6. Maker は検証済みポートフォリオ（Receipt の束）を得て、受注文脈で共有できる。

### B. Buyer / 発注者: 主張を検証する
1. Maker から Receipt / ポートフォリオのリンクを受け取る。
2. 機械再計算メトリクス（強）と顧客アテステーション（弱）が分離表示される。
3. 署名・コミットメントを**自分で（または公開検証ツールで）再現検証**。秘密本文は見えない。

### C. Reviewer（縮小）: 機械再計算できない部分だけ
- CVR 等・主観品質のみ、ルーブリックで署名判定。機械で再計算できるものは Reviewer を通さない。

## 8. Phase plan（書き直し）

- **Phase 0（1–2 週）資産の検証:** synthetic Trace + 手動 redact で、実在案件1件の Receipt を紙で作り、Maker 10 人に「受注に使いたいか」を聞く。Kill line = 6 人未満。
- **Phase 1（2 週）Receipt 発行パイプライン:** パスキー、ローカル redact + 承認 UI、Trace / Receipt スキーマ、Web 制作評価器アダプタ（`reexec-core` 上）。チェーン無しでも第三者再現検証が成立すること。
- **Phase 2（1–2 週）アンカー + 検証者独立性:** `ReceiptRegistry` へコミットメント + 検証者署名をアンカー、公開検証ツール。
- **Phase 3（後続・柱1）:** ここで初めて Capsule 再利用・License・エスクロー・ロイヤリティを、成立した信用の上へ接ぐ。

## 9. Kill criteria（柱2版）

- redact 後の Receipt を、Maker が「受注に使う価値がある」と見なさない（＝実績が秘密文脈から分離できない）。
- 機械再計算メトリクスが、汎用の「AI 使ってます」自己申告と実質差別化にならない（買い手が信用の根拠として読まない）。
- 意味のあるメトリクス（CVR 等）が結局どれも独立再計算できず、全部が顧客アテステーション頼み（＝ただの署名付き自己申告に退化）。
- 検証者独立性が保てない（Maker と検証者を分離できず、再計算が自己申告に崩れる）。

---

**残る本質リスク（正直に）:** 「機械再計算できるメトリクス（Lighthouse 等）は差別化として弱く、差別化になるメトリクス（CVR 等）は独立再計算できない」という緊張が柱2の核心的リスク。Phase 0 は、この緊張の中に *買い手が信用の根拠として読む Receipt* が実在するかを測るためにある。ここが割れたら柱2も畳む。
